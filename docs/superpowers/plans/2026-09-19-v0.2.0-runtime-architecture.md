# ResourcePortal v0.2.0 runtime architecture implementation plan

## Goals

- one public API process with no Docker daemon or host-storage access,
- one durable background Worker owning infrastructure side effects,
- one Operation queue for deployments, volumes, runtime actions and platform reconciliation,
- worker-owned observed-state reconciliation persisted in PostgreSQL,
- App Group network isolation and explicit tenant-workload node capability,
- encrypted App Group Secret payloads stored in PostgreSQL instead of filesystem dual-write,
- upgrade compatibility from v0.1.8/v0.1.9/v0.1.10, including legacy filesystem Secret migration,
- keep storage HA, first-class backup/restore and Traefik Docker-socket proxy outside v0.2.0.

## Compatibility rules

- preserve existing HTTP resource/deployment views where possible,
- preserve AppGroupDeployment as deployment history/snapshot data while Operation becomes execution ownership,
- keep legacy deployment lease columns readable during upgrade but stop using the deployment queue as the primary scheduler,
- make new Secret DB payload nullable during migration and lazily/proactively backfill from legacy files in Worker,
- Worker temporarily retains legacy Secret filesystem read access for upgrade migration; API does not,
- migrations must be additive/non-destructive for supported upgrades.

## Verification gates

1. Prisma generate + migration validation.
2. API unit tests and new worker/executor tests.
3. Installer rendering/upgrade tests for one Worker and API mount removal.
4. Full repository lint, test, build.
5. Installer test suite.
6. Real/dedicated E2E upgrade path if the dedicated E2E host is reachable.
